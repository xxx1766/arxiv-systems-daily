#### [1]. ARK: Avoiding Routing Collisions for KV Cache Transfer in Disaggregated LLM Inference
- **中文译名**：ARK：在大模型解耦推理中避免 KV Cache 传输的路由冲突
- **链接**：https://arxiv.org/abs/2610.41160
- **作者**：Hung-Chun Lin, Ting-Wei Hsu, Chung-En Ho, Ahmed Saeed
- **单位**：佐治亚理工学院（Georgia Institute of Technology）【知名实验室】
- **分类**：cs.DC, cs.NI
- **方向标签**：AI Infra-推理系统 / 云原生网络
- **相关度**：★★★★★（5/5）

1. **核心贡献**：解决了当前大模型 PD 分离（Prefill 与 Decode 节点拆分）推理架构中，跨节点传输海量 KV Cache 时因传统网络 ECMP 随机哈希冲突导致网络丢包和尾延迟暴增的核心痛点。
2. **原理解析**：在 PD 分离架构下，Prefill 实例把计算好的 KV Cache 发送给 Decode 实例就像在网络里运送一列“超级重载列车”（持续数百毫秒到数秒的大象流）。传统数据中心交换机用 ECMP 随机选路，很容易让两条重载列车撞在同一个 Spine 交换机端口上引发拥堵。ARK 就像一个**轻量级发车调度员**：在发送端通过协调各个发送方的源端口号（Source Port），借由特定哈希映射主动把并发的大流打散分流到不同的 Spine 路径上，既不需要改造底层交换机硬件，也不需要在接收端引入乱序重排机制。
3. **关键结论**：在基于 RDMA 的网络仿真实验中，相较于标准 ECMP，ARK 在中等负载下将流传输完成时间（FCT）的平均值和 P95 分别降低了 **27.3%** 和 **34.0%**，并将 LLM 的首字延迟（TTFT）降低了 **12.9%**。提升原因在于彻底消除了长周期大象流在多路径路由上的热点瓶颈。
4. **背景地位**：
   - 基于代表性工作：DistServe、Splitwise 等 PD 分离经典工作，以及数据中心经典拥塞控制协议。【论文明确提及】
   - 后续影响：对云原生 CNI 插件优化、AI 专用网络协同调度调度器设计具有重要的落地参考价值。【基于领域常识推测】
5. **落地相关性**：
   - **关联点**：直接关联 K8s 集群中 vLLM/SGLang 等解耦部署时的 Pod 间 RDMA/RoCE 通信瓶颈。
   - **能否借鉴到 K8s/云原生体系**：**可以**。不需要定制专用交换机固件，可以通过在 Pod 网络侧注入 Sidecar 或 CNI 驱动层实现源端口的协同调度。
   - **建议先读**：§3 System Design（详细解析如何零硬件开销完成跨节点端口协调）。
   - **是否开源**：未发现开源仓库链接。

#### [2]. LLM Fine-Tuning Workloads: Characterization, Challenges, and Opportunities for Serverless AI
- **中文译名**：大模型微调工作负载：Serverless AI 的特征画像、挑战与机遇
- **链接**：https://arxiv.org/abs/2610.40983
- **作者**：Radu Nicolae, Daniele Lotito, Alexandru Iosup
- **单位**：阿姆斯特丹自由大学（Vrije Universiteit Amsterdam）, IBM Research Europe【工业界】
- **分类**：cs.DC
- **方向标签**：容器与运行时-Serverless / AI Infra-训练系统
- **相关度**：★★★★★（5/5）

1. **核心贡献**：填补了业界对大模型微调在 Serverless 场景下真实运行态画像的认知空白，首次量化揭示了因资源配置不当导致的极高训练任务失败率与集群资源浪费。
2. **原理解析**：Serverless 理念是“用户只管提交微调数据，平台自动分配算力并按需伸缩”。但 LLM 微调如同在有限尺寸的集装箱内动态塞入易膨胀的货物（显存占用随时可能因 Batch Size 或激活值激增而 OOM）。作者团队分析了涵盖 4 种主流 GPU、1 至 32 卡规模的 30,920 次真实微调实验，系统性地勾画出了模型规模、通信拓扑与配置参数之间的边界规律。
3. **关键结论**：
   - **极高的脆弱性**：微调任务的存活率严重受 Batch Size 影响，在小 Batch 下失败率约为 52%，而在 1,024 大 Batch 下因显存溢出等配置原因**失败率高达 95%**；
   - **系统层优化碾压模型层**：节点间引入 RoCE 网络可带来高达 **2.9 倍**的通信效率提升（效率从 0.26 飙升到 0.72），其收益显著超过了 Fast MoE 等应用层算法优化（仅 1.7 倍）。
4. **背景地位**：
   - 基于代表性工作：IBM LLMFineTuningBench 数据集、Ray 以及主流分布式微调框架（PEFT/LoRA）。【论文明确提及】
   - 后续影响：将直接指导下一代面向大模型微调的 Serverless 运行时调度算法和自动防 OOM 超卖策略。【基于领域常识推测】
5. **落地相关性**：
   - **关联点**：与基于 K8s 的 Serverless 平台（如 Knative）、AI 训练 Operator（如 Kubeflow/Volcano）的资源配额（Requests/Limits）估算直接相关。
   - **能否借鉴到 K8s/云原生体系**：**可以**。结论直接支持了在 K8s 调度器中引入“基于经验参数的准入控制与自动降级（Auto-Batch Tuning）Controller”。
   - **建议先读**：§4 Empirical Findings 与 §5 Serverless Opportunities。
   - **是否开源**：IBM 开源了数据集与评估基准（LLMFineTuningBench）。

#### [3]. HiState: Hierarchical Prefix Cache Management for Hybrid LLM Serving in Agentic Workloads
- **中文译名**：HiState：面向 Agent 工作负载的混合大模型分层前缀缓存管理
- **链接**：https://arxiv.org/abs/2610.41508
- **作者**：Zaifeng Pan, Lucas Wang, Xinwei Qiang, Yanbo Zhou, Chang Chen, 等, Yufei Ding
- **单位**：加州大学圣地亚哥分校（UCSD）【知名实验室】
- **分类**：cs.DC, cs.AI
- **方向标签**：AI Infra-推理系统 / 编排与调度
- **相关度**：★★★★★（5/5）

1. **核心贡献**：攻克了在混合架构模型（如 Mamba/Transformer 结合的混合模型）服务中，Agent 多轮回溯改写上下文时导致的 Checkpoint 显存膨胀与前缀缓存（Prefix Cache）命中率大幅下降难题。
2. **原理解析**：传统的 Prefix Cache 类似把每次与容器的交互历史缓存在内存，随时准备“从快照恢复”。但智能体（Agent）经常需要撤销、修改旧计划或者分支探索，传统的线性 Checkpoint 机制一旦分支，就不得不重新计算。HiState 敏锐地发现：**无论历史有多少个 Checkpoint，模型恢复一次只需要一个最近的状态点**。因此 HiState 像操作系统 Page Cache 分层一样，把历史 Checkpoint 卸载到廉价的高速 NVMe SSD 上，而宝贵的 GPU 显存专供活跃的 KV 缓存，按需换入。
3. **关键结论**：在两个真实的 Coding Agent 数据集实测中，HiState 相比于 vLLM-Marconi 和 SGLang-HiCache，在长尾请求的 **p99 首字延迟（TTFT）上分别实现了最高 5.73 倍和 5.44 倍的加速**，有效消除了显存争抢。
4. **背景地位**：
   - 基于代表性工作：vLLM、SGLang、RadixAttention 以及混合架构模型（Jamba 等）。【论文明确提及】
   - 后续影响：为 LLM 推理系统在本地盘、主机内存与 GPU 显存之间的跨层级缓存编排提供了成熟的范式。【基于领域常识推测】
5. **落地相关性**：
   - **关联点**：与推理 Pod 的本地临时存储（HostPath / Ephemeral Storage）配合使用，涉及节点级缓存驱逐管理。
   - **能否借鉴到 K8s/云原生体系**：**部分可以**。虽然属于推理引擎内核优化，但集群层面的存储挂载策略（为推理节点挂载本地 NVMe）是其发挥效能的前提。
   - **建议先读**：§3 Architecture and Tiered Storage Design。
   - **是否开源**：基于 vLLM 实现，代码计划开源。

#### [5]. LEAP: Efficient LLM Inference Scheduling with Generalizable Length Prediction
- **中文译名**：LEAP：基于泛化长度预测的高效大模型推理请求调度

- **作者**：Kwan Yan, Jialun Zhong, Yanzeng Li
- **单位**：北京邮电大学（BUPT）
- **分类**：cs.LG, cs.AI
- **方向标签**：编排与调度 / AI Infra-推理系统
- **相关度**：★★★★☆（4/5）

1. **核心贡献**：攻克了 LLM 推理调度中“最短作业优先（SJF）”策略依赖大模型预测输出长度时开销大、跨域任务泛化差并拖慢系统整体吞吐的难题。
2. **原理解析**：大模型服务排队调度如果能先做“短任务”，平均等待延迟就会极低。但预测一个 Prompt 会生成多少个 Token，过去要么用庞大的辅助模型（自身就要消耗 GPU），要么预测不准导致排队混乱。LEAP 就像**就地取材的轻量级调度探针**：直接复用推理模型在 Prefill 阶段生成的隐层状态（Hidden States），利用 CPU 端异步轻量级线性回归头提取长度特征，不仅完全不抢占 GPU，而且在遇到未知领域任务时通过递归最小二乘法进行零梯度的实时在线自适应。
3. **关键结论**：在跨域推理评测中，LEAP 将单 Token 平均延迟降低了 **15.9%–40.8%**，推理吞吐量提升了 1.9%，而**预测器参数量比最强基线小了 30,569 倍**。
4. **背景地位**：
   - 基于代表性工作：FastServe、Orca 等基于迭代级调度的经典 LLM Serving 框架。【论文明确提及】
   - 后续影响：为 LLM 推理 Gateway 和网关层调度器提供了极具性价比的轻量决策方案。【基于领域常识推测】
5. **落地相关性**：
   - **关联点**：与云原生 AI 网关（如 Envoy/Higress/Knative）的流量分发策略、请求优先级队列调度直接相关。
   - **能否借鉴到 K8s/云原生体系**：**可以**。可作为 Ingress / AI Gateway 的请求分发策略插件。
   - **建议先读**：§3 Methodology (Online Adaptation & CPU-GPU Asynchronous Execution)。
   - **是否开源**：未发现开源仓库链接。
